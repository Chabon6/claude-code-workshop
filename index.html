01 · Skill 基礎

如果你一直重講同一件事，就把它存成 Skill

Skill 是一套可重複使用的工作方法。當你每次都貼上相同指示、檢查清單、格式要求或步驟，就值得考慮做成 Skill。

每次重講

規則容易漏，品質容易飄

你必須記得每次要提醒 Claude 什麼。少講一條，結果就可能不同。

存成 Skill

把工作方法固定下來

Claude 遇到相關任務時，可以載入同一套步驟、判斷規則和交付標準。

Skill 結構

Skill 是一個資料夾，入口是 SKILL.md

my-skill/
├── SKILL.md          # 必要：metadata + 工作指示
├── scripts/          # 選用：可執行程式
├── references/       # 選用：參考資料
└── assets/           # 選用：模板或其他素材
A

Metadata（名稱與用途描述）

name 和 description 放在 YAML frontmatter。用途描述說清楚 Skill 做什麼、什麼時候該用。

B

SKILL.md 內文（工作指示）

Skill 啟用後，Claude 才載入完整工作方法。其他參考資料則在需要時再讀。

P

專案 Skill

.claude/skills/<skill-name>/SKILL.md

U

個人 Skill

~/.claude/skills/<skill-name>/SKILL.md

不用從空白檔案開始

Anthropic 官方的 Skill Creator 可以協助你釐清需求、起草、測試和修改。你最重要的工作，是把自己的工作方法講清楚。

Lesson A

Skill 不需要很複雜，才值得做

只要你每次都在重講同一套格式、檢查清單或邊界規則，就可以先把它存起來。

02 · 專業判斷

真正有價值的，是 Claude 原本不知道的判斷

好的 Skill 不只告訴 Claude「做什麼」，還要告訴它「怎麼判斷做到什麼程度才可以交付」。

1

步驟

事情照什麼順序做？哪些步驟不能跳？

2

判斷

什麼重要？什麼異常？什麼情況值得繼續追？

3

例外

什麼情況不能照一般規則？資料互相衝突時怎麼辦？

4

完成標準

做到什麼程度，才真的可以交出去？

太空泛
仔細檢查資料
找出重要趨勢
保持專業與正確
交付前再次確認
有判斷規則
先看商業影響，不要只看變動百分比
把已確認事實和推測分開
來源衝突時，標示衝突並升級處理
重要數字沒有和來源核對前，不要交付
案例 B · 判斷密集

報告品質系統性提升作戰手冊

真實專案

這是一個純靠 AI 產出報告的專案。最大的風險不是程式報錯，而是 AI 沒有忠實遵循品質規則、或外部事實沒有真的查證，品質就會悄悄變差。這個風險曾經真的發生過：一份正式報告完全繞過品質檢查。

Why this Skill exists

不是每次看到錯誤就頭痛醫頭

這份 Skill 把散落在不同地方的品質機制、真實量測基準，以及每輪品質提升要怎麼繼續，收斂成一份可以反覆打開的「專案品質記憶」。

Inside the Skill

打開這份作戰手冊，你會看到六塊內容

個股、投資判斷與實際量測數值不在教材展示；以下保留 Skill 的工作結構與判斷邏輯。
01前置閘門先確認地基有沒有壞，再看任何分數＋

有幾項前置條件必須先修好。最重要的兩件事是：品質流程有沒有真的跑到，以及外部事實有沒有真的被查證。

如果前置條件沒過，後面量出來的數字就沒有意義。

核心判斷：先把地基打好，再談優化。
02已建好的品質槓桿先知道專案現在有哪些防線＋

作戰手冊會盤點目前已存在的品質機制，例如初始協調規則、事實查證規則與評分規則。

這讓你下一次要改善品質時，不必重新靠記憶拼湊「我們到底已經做過什麼」。

03真實量測基準用多輪審查紀錄判斷品質是否真的收斂＋

手冊內建一組真實的同行審查逐輪紀錄：

  • 第一輪抓到最多、最嚴重的錯誤
  • 中間幾輪開始轉成方法論類問題
  • 最後一輪只剩風格類意見，而且分數不再變動
這組基準回答：現在還在修真正的品質問題，還是已經接近收斂？
04每輪品質提升要做的 5 件事每一輪都有固定打法，不是臨場想到什麼就修什麼＋

這份 Skill 直接把「每跑一輪品質提升時要做的 5 件事」寫進作戰手冊。這讓品質改善變成可以重複執行的回合，而不是發現一個錯就只修一個錯。

課堂上不需要背這 5 個子步驟；真正值得注意的是：連「下一輪怎麼打」都被保存下來了。

05尚未建置的候選改進聽起來應該有用，不代表已經有效＋

有些改善點子會被明確標記為 Candidate（候選），而不是假裝已經完成。

除非它真的在一次實戰裡被證明需要，否則就維持候選，不急著加進正式流程。

這是在對抗過度工程：已驗證的能力和「聽起來可能有用」的點子要分開。
06重新驗證這份手冊Skill 不是寫完就永遠不變＋

文件結尾還附了一組具體指令，用來重新驗證這份作戰手冊是不是已經過時。

這代表 Skill 本身也要被維護：品質機制改了、基準變了，Skill 也應該跟著更新。

Judgment inside the Skill

這份手冊真正保存的是五種方法論判斷

1

順序判斷

先修前置問題，再測後面的品質。順序錯了，數字就可能是假象。

2

誘因設計

完成一輪審查只給小額加分，但每留下一個未修正的嚴重錯誤就扣更大的分數，讓「偷懶跳過修正」變得不划算。

3

準確優先於分數

即使修正事實會讓分數下降，也要保留修正。分數好看不能凌駕於準確。

4

查不到，就說未核實

外部事實查不到時，不要裝出信心。明確標示「未核實」，比給一個看似肯定的答案更專業。

5

知道什麼時候停止

當實質錯誤與方法論問題逐輪消失，最後只剩風格意見、分數也不再變動，就有理由判定已經收斂。

Lesson B

Skill 不只可以保存判斷標準
也可以保存「品質戰打到哪裡」

包含已經做過什麼、真實基準線在哪、還有哪些候選改善，以及下一輪要怎麼繼續。

03 · 動手做 · 25 分鐘

現在，把一件你真的做過的工作變成 Skill

不要挑「看起來很酷」的題目。挑一件之後還會再做，而且你分得出好結果和壞結果的工作。

1

選

選一件會重複出現，而且已有固定做法的工作。

2

教

讓 Skill Creator 訪談你。提供真實例子、判斷規則、例外和常見錯誤。

3

建

讓 Skill Creator 起草，再確認它有沒有真的抓到你的工作方法。

起手 Prompt
Use the skill-creator skill to help me turn the following recurring work into a reusable Skill.

Do not draft immediately. First interview me about:
- when this task should trigger
- inputs and outputs
- how I make decisions
- exceptions and edge cases
- what bad output looks like
- what “good enough to send” means

My recurring task is: [describe your task]
  • 選的是自己真的做過的工作。
  • 至少提供一個真實輸入、輸出或具體情境。
  • 至少說出一條「新人不一定知道」的判斷規則。
  • 至少說明一個例外或常見錯誤。
  • 說清楚什麼叫「可以直接交付」。
04 · 測試與改進

第一版不用完美，但一定要拿真實情境試

這堂課至少試兩種情境：一個正常案例，再加一個有缺漏、衝突或例外的困難案例。

N

正常情境

確認 Skill 會被正確使用，而且基本流程能走完。

D

困難情境

加入資料缺失、來源矛盾或例外，測出 Skill 缺少哪些判斷。

看到的問題優先檢查
該用卻沒用用途描述和觸發條件
用了但做法不對工作步驟、判斷規則和參考資料
看起來合理，但不能直接交完成標準、品質檢查和範例

案例 C · 自動化

每日盤前熱股掃描與推播

真實自動化

這套系統會在每天盤前自動掃描台美股熱門標的、整合多個情報來源，再由專職 AI 子代理判斷題材是「剛升溫／高潮／退燒」，最後自動發出整理好的訊息。

H

高頻率

每天都要做。

T

時間敏感

必須在盤前完成。

S

流程固定

每天內容不同，但流程固定。

Two-layer architecture

這套 Skill 分成「執行層」和「支援層」

執行層負責每天真的怎麼跑；支援層則保存為什麼這樣設計、以前壞過什麼，以及平常怎麼維護。

Inside the Skill · 執行層

原 Skill 是完整的 8 步驟協定

公開版先看流程摘要；重點是理解每一層如何把下一層需要的資訊準備好。

1 / 7
01SCREEN

量化篩選

先用量化條件縮小候選範圍。

02FEEDBACK

命中率回填 / 週報

把過去執行結果回填，並保留週期性回顧。

03SOURCES

七個情報來源各自抓取

七個來源彼此獨立。一個來源掛掉，不會拖累其他來源。

04VALIDATE

訊號萃取與驗證

不合格資料直接拒收，不強行塞進結果。

05JUDGE

專職子代理做強度裁決

由一個純推理、不使用任何工具的 AI 子代理，把題材分成「剛升溫／高潮／退燒」。如果裁決失敗，還有明確的兩階段退階方案。

06COMPOSE

組成訊息 + 發送前品質檢查

輸出必須符合固定格式契約，並在發送前再做品質檢查。

07DELIVER

發送並寫入成功標記

只有真正發送成功，才寫入成功狀態。

實際 webhook、API 金鑰、股票代碼與投資判斷不在教材展示。
Inside the Skill · 支援層

三份文件，各自只管一件事

它們刻意不互相重複，讓未來維護時知道該去哪裡找答案。

WHY設計意圖這套系統為什麼這樣設計＋

記錄原本的設計理由，避免未來只看到現在的做法，卻不知道當初為什麼做這些取捨。

BUG故障目錄以前踩過哪些坑、怎麼修＋

把真實故障模式與修法留下來，避免未來再次踩到同一個坑。

OPS日常運維平常怎麼維護它＋

保存日常運維方式，讓這套系統不是「做完就忘」。

Important design choices

無人值守，不代表只要把排程打開就好

1

互動模式能跑，不代表自動模式能跑

無人值守環境必須實際探測，不能用「我在旁邊操作時可以」直接推論。

2

多層降級，不是全有全無

情報來源或子代理失敗時，有明確退階路徑；資料不完整可以，但不能假裝完整。

3

把「絕對不要做什麼」寫清楚

例如發送失敗不能寫成功標記，外部抓回來的文字也不能被當成系統指令。

4

誠實記錄安全邊界

執行協定明確承認目前的權限控管仍有已知殘餘風險，沒有把系統描述成無懈可擊。

曾經真實運行

不是紙上設計

有生產環境執行紀錄與狀態時間戳，證明它曾經在一段時間內每天自動執行。

目前狀態

已建置、已驗證、目前暫停

負責排程觸發的常駐程序目前沒有運行。自動化做完之後，仍然需要有人確認它是否還活著。

一次真實失敗

「我在旁邊操作時能跑」
不代表「沒人在旁邊時也能跑」

第一次無人值守執行

系統在極短時間內結束，沒有錯誤訊息，也沒有產出。表面上看起來像「什麼都沒發生」。

不要猜，直接做一比一探測

把幾種不同呼叫方式分別放進互動模式與無人值守模式實測。

找到根因

某個在互動模式能正常運作的捷徑，在無人值守模式被靜默解析成空任務，所以模型其實收到的是「什麼都沒有」。

修好，也防止復發

改成明確、直接、不依賴捷徑的呼叫方式，再加一條自動化測試，防止未來有人為了簡化又改回去。

Lesson C

自動化拿掉的是「誰來按開始」
不是專業判斷

Case C 仍然保留訊號驗證、強度裁決、退階與品質門檻，只是把觸發這件事也交給系統。
