01 · Skill 基礎

如果你一直重講同一件事，就把它存成 Skill。

Skill 是一套可重複使用的工作方法。當你每次都貼上相同指示、檢查清單、格式要求或步驟，就值得考慮做成 Skill。

每次重講

規則容易漏，品質容易飄

你必須記得每次要提醒 Claude 什麼。少講一條，結果就可能不同。

存成 Skill

把工作方法固定下來

Claude 遇到相關任務時，可以載入同一套步驟、判斷規則和交付標準。

Skill 結構

Skill 是一個資料夾。入口是 SKILL.md。

my-skill/
├── SKILL.md          # 必要：metadata + 工作指示
├── scripts/          # 選用：可執行程式
├── references/       # 選用：參考資料
└── assets/           # 選用：模板或其他素材
A

Metadata（名稱與用途描述）

name 和 description 放在 YAML frontmatter。用途描述說清楚 Skill 做什麼、什麼時候該用。

B

SKILL.md 內文（工作指示）

Skill 啟用後，Claude 才載入完整工作方法。其他參考資料則在需要時再讀。

P

專案 Skill

.claude/skills/<skill-name>/SKILL.md

U

個人 Skill

~/.claude/skills/<skill-name>/SKILL.md

不用從空白檔案開始。

Anthropic 官方的 Skill Creator 可以協助你釐清需求、起草、測試和修改。你最重要的工作，是把自己的工作方法講清楚。

會議筆記 → 可直接寄出的會後摘要

現場示範

Lesson A

Skill 不需要很複雜，才值得做。

只要你每次都在重講同一套格式、檢查清單或邊界規則，就可以先把它存起來。

02 · 專業判斷

真正有價值的，是 Claude 原本不知道的判斷。

好的 Skill 不只告訴 Claude「做什麼」，還要告訴它「怎麼判斷做到什麼程度才可以交付」。

1

步驟

事情照什麼順序做？哪些步驟不能跳？

2

判斷

什麼重要？什麼異常？什麼情況值得繼續追？

3

例外

什麼情況不能照一般規則？資料互相衝突時怎麼辦？

4

完成標準

做到什麼程度，才真的可以交出去？

太空泛
仔細檢查資料。
找出重要趨勢。
保持專業與正確。
交付前再次確認。
有判斷規則
先看商業影響，不要只看變動百分比。
把已確認事實和推測分開。
來源衝突時，標示衝突並升級處理。
重要數字沒有和來源核對前，不要交付。
案例 B · 判斷密集

把報告品質標準做成一份作戰手冊

真實專案

AI 報告最危險的問題，不一定會報錯。有時流程被跳過、事實沒有查證，報告看起來仍然很正常，但品質已經下降。

Inside the real Skill

先看原則；點開後看 Claude 實際怎麼執行。

展開內容改成「何時觸發 → 檢查什麼 → 做什麼 → 何時停止」，避免只把抽象原則換句話說。

以下依真實 Skill 結構脫敏重建；保留工作邏輯，不公開真實股票、研究結論或量測數值。
01先修地基前置品質機制沒跑，後面的分數先不要看＋
WHEN準備開始一輪品質改善時

不要直接拿現有報告進評分。

CHECK先確認前置品質閘門

品質審查流程有沒有真的執行？外部事實查證有沒有被跳過？必要 review 是否存在？

IF FAIL任一閘門失敗，就停止評分

先修被繞過的流程，再重新產生／審查結果。

IF PASS全部通過，才進 benchmark

此時後面的分數與 finding 才有比較意義。

OPERATING RULEgate failure → repair process → rerun quality path → only then score
02保存品質機制盤點每次開工先知道：哪些已建、哪些要重驗、哪些只是候選＋
LOAD讀目前品質槓桿清單

例如：初始協調規則、事實查證規則、同行審查、評分機制。

CLASSIFY每一項都有狀態

已建置需要重驗候選改善

DO優先驗證既有機制是否仍有效

不要看到新問題就立刻再新增一層規則。

DON'T不要把 Candidate 當成既成能力

未經實戰證明前，狀態保持候選。

這讓 Skill 保存的是「專案品質記憶」，不是一張靜態 checklist。

03用真實基準判斷是否收斂每輪不是看感覺，而是看 finding 類型是否真的下降＋
EACH ROUND跑一輪審查並分類 finding

分清楚實質錯誤、方法論問題、風格偏好，不把所有意見混在一起。

COMPARE和歷史基準比

前幾輪通常抓到高影響問題；後面如果只剩 style，代表可能已接近收斂。

CONTINUE IF仍有新的實質／方法論問題

修正後再跑下一輪。

STOP IF核心問題不再出現，且分數不再實質改善

不要為了風格偏好無限重跑。

CONVERGENCE SHAPEmaterial findings ↓ → methodology findings ↓ → style-only → stop
04正確比高分重要Skill 保存價值排序，也包含「不要為了分數偷懶」的誘因＋
SCORE DESIGN完成一輪審查只給小額正向回饋

單純「有跑流程」不值得大量加分。

PENALTY留下未修正的嚴重錯誤，扣分要更重

讓「跳過修正」在機制上變得不划算。

TRADE-OFF修正事實即使讓總分下降，也保留

因為分數只是代理指標，不是真實品質本身。

PRIORITYAccuracy > Score

先保真實性，再談漂亮 KPI。

DECISIONif factual correction lowers score → keep the correction
05候選不等於已驗證新點子先當假設；只有實戰需要且驗證有效，才升級＋
NEW IDEA把新改善先標成 Candidate

記錄它想解決的問題，但先不當作正式流程。

TRIGGER等真實案例再次暴露需求

只有「實際需要」才值得投入建置。

VERIFY建置後再跑真實案例驗證

有效才升級；無效就撤回或繼續保持候選。

DON'T不要因為「聽起來很聰明」就加進正式流程

避免過度工程，也避免 Skill 越寫越肥。

LIFECYCLEcandidate → real need → implement → verify → promote / reject
真實 Skill 還包含量測基準來源、品質槓桿出處與重新驗證指令；本頁只展示足以理解方法的脫敏片段。
1

順序判斷

先修地基，再談優化。

2

價值取捨

正確比高分重要。

3

停止判斷

知道什麼時候已經夠好。

Lesson B

不要只教 Claude 做什麼，也要教它怎麼判斷「夠好了」。

這個 Skill 保存的不只是規則，而是專案到目前為止的品質記憶、基準和下一步。

03 · 動手做 · 25 分鐘

現在，把一件你真的做過的工作變成 Skill。

不要挑「看起來很酷」的題目。挑一件之後還會再做，而且你分得出好結果和壞結果的工作。

1

選

選一件會重複出現，而且已有固定做法的工作。

2

教

讓 Skill Creator 訪談你。提供真實例子、判斷規則、例外和常見錯誤。

3

建

讓 Skill Creator 起草，再確認它有沒有真的抓到你的工作方法。

起手 Prompt
Use the skill-creator skill to help me turn the following recurring work into a reusable Skill.

Do not draft immediately. First interview me about:
- when this task should trigger
- inputs and outputs
- how I make decisions
- exceptions and edge cases
- what bad output looks like
- what “good enough to send” means

My recurring task is: [describe your task]
  • 選的是自己真的做過的工作。
  • 至少提供一個真實輸入、輸出或具體情境。
  • 至少說出一條「新人不一定知道」的判斷規則。
  • 至少說明一個例外或常見錯誤。
  • 說清楚什麼叫「可以直接交付」。
04 · 測試與改進

第一版不用完美，但一定要拿真實情境試。

這堂課至少試兩種情境：一個正常案例，再加一個有缺漏、衝突或例外的困難案例。

N

正常情境

確認 Skill 會被正確使用，而且基本流程能走完。

D

困難情境

加入資料缺失、來源矛盾或例外，測出 Skill 缺少哪些判斷。

看到的問題優先檢查
該用卻沒用用途描述和觸發條件
用了但做法不對工作步驟、判斷規則和參考資料
看起來合理，但不能直接交完成標準、品質檢查和範例
05 · 自動化

Skill 決定怎麼做；自動化決定什麼時候做。

先把工作方法做穩，再考慮排程或事件觸發。否則只是把不穩定的流程跑得更勤。

HOWSkill

案例 C · 自動化

每日盤前情報工作流

真實自動化

這套系統曾在每天盤前自動整理台美股熱門標的。它值得自動化，因為同時具備：高頻率、有時效、流程穩定。

H

高頻率

每天都要做。

T

有時效

晚了，價值就下降。

S

流程穩定

內容每天不同，但處理方法固定。

Inside the automated Skill

左右滑：看完整 8 步驟執行協定

手機直接滑動；桌機可用左右按鈕。

1 / 8
01SCREEN

量化篩選

先用固定條件縮小候選範圍，避免所有資訊一股腦交給後面的判斷。

目的：先降低噪音，再做深度分析。
02FEEDBACK

回填結果與週期回顧

把過去結果留下來，讓系統知道哪些訊號曾經有效，而不是每天失憶重來。

Skill 可以保存「目前做到哪裡」，不只保存 SOP。
03SOURCES

多來源獨立抓取

七個情報來源彼此獨立。一個來源掛掉，不讓其他來源一起失敗。

設計原則：故障隔離，而不是全有全無。
04VALIDATE

萃取與驗證訊號

不是抓到就收。證據不足的資訊直接拒收，不為了「看起來完整」強行塞進結果。

品質規則：不完整可以，假完整不行。
05JUDGE

AI 子代理做強度裁決

專職推理代理把題材分成「剛升溫／高潮／退燒」。裁決失敗時有明確退階方案。

自動化沒有拿掉 judgment；它把 judgment 結構化了。
06COMPOSE

組成訊息

依固定格式把來源、訊號與判斷整理成一則可以直接閱讀的盤前訊息。

格式契約讓下游不用重新猜內容在哪。
07QUALITY

發送前品質檢查

確認輸出符合必要條件，缺資料時要明確標示，而不是假裝完整。

Automation 前仍然需要 Definition of Done。
08DELIVER

發送 + 成功標記

只有真正發送成功才寫成功狀態；發送失敗不能留下假的成功紀錄。

系統狀態本身也是品質的一部分。
提示：這是依真實 8 步驟協定脫敏重建；股票、訊息目的地與憑證均未公開。
Supporting memory

真正的系統不只有一份 Skill

點開三塊支援記憶，看看它怎麼避免「做完就忘」。

WHY設計意圖為什麼系統要這樣做＋

保存原始設計理由。未來修改時，不只知道「現在長這樣」，還知道當初為什麼這樣設計。

BUG故障與修復記憶以前踩過哪些坑＋

包含曾經發生過的 silent failure、怎麼定位、怎麼修，以及哪個 regression test 用來防止復發。

OPS日常運維平常怎麼確認它還活著＋

保存日常維護方式。Automation 建好不代表永遠正常；健康檢查也是系統的一部分。

一次真實失敗

「我在旁邊操作時能跑」不代表「沒人在旁邊時也能跑」。

第一次無人值守執行

程式很快結束。沒有錯誤，也沒有產出。

不要猜，直接測

把不同啟動方式在互動模式與無人值守模式逐一實測。

找到原因

某個互動模式可用的捷徑，在無人值守模式被安靜地解析成空任務。

修好，也防止復發

改用跨環境都可靠的明確呼叫方式，再加 regression test。

Lesson C

自動化拿掉的是「誰來按開始」，不是專業判斷。

沒有人在旁邊時，工作方法反而更需要寫清楚、測清楚，還要先想好失敗時怎麼處理。

收尾

下一個 Skill，從你明天還會做的工作開始。

  • 這件事之後還會再發生嗎？
  • 我是不是每次都在重複提醒 Claude 同樣的事？
  • 這件事有沒有「我知道，但新人未必知道」的判斷？
  • 我能不能說清楚什麼結果才算可以交付？
