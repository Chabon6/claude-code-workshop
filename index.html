01 · Skill basics

不要一直重新教 Claude 同一件事。

當你一再貼上相同 instructions、checklist、格式要求或 multi-step procedure，通常就是 Skill candidate。

Repeated prompting

每次重新解釋

容易漏項、標準飄動，而且使用者必須記得每次要講什麼。

Reusable skill

把方法存一次

Claude 在相關任務出現時，載入固定工作方法、判斷規則與交付要求。

Anatomy

Skill 是資料夾，不只是長 Prompt。

my-skill/
├── SKILL.md          # 必要：metadata + instructions
├── scripts/          # 選配
├── references/       # 選配
└── assets/           # 選配
A

Description

說清楚 Skill 做什麼、何時該用。它是 triggering 的重要訊號。

B

Instructions

Skill 被使用時才載入主體工作方法；reference 資料按需要再讀。

不要從空白檔案開始。

Anthropic 官方的 skill-creator 可以幫你釐清需求、起草、測試與迭代。課堂真正要學的，是把工作知識說清楚。

Case A · Simple

Meeting Notes → Follow-up Brief

LIVE DEMO

這個案例刻意很簡單：不追求「聰明」，只把每次都要重講的格式與邊界固定下來。

Before

每次提醒 Claude：整理決策、待辦、未解問題、下次追蹤；而且不要亂補 owner、deadline，也不要把討論中的 idea 寫成 confirmed decision。

After

Skill 固定輸出 Decisions / Action Items / Open Questions / Next Follow-up；沒有出現在筆記裡的 owner 或 due date 就寫「未指定」。

Demo input
產品更新會議
- 決定 9/1 先推出 beta
- Amy 說可以研究邀請制，但還沒決定
- Jason 要整理 onboarding FAQ，下週三前給初稿
- 行銷素材誰負責還沒定
- 下次會議 8/30 下午 2 點
Lesson A

Skill 不一定要很「聰明」才值得做。

只要你每次都在重講同一套格式、檢查清單或邊界規則，就已經值得把它存起來。

02 · Judgment

真正值錢的是 Claude 原本不知道的那一層。

好的 Skill 不只保存「做什麼」，還保存「你怎麼知道它做得夠不夠好」。

1

Steps

事情依什麼順序做？哪些步驟不能跳？

2

Judgment

怎麼判斷重要／不重要、正常／異常、是否值得深入？

3

Exceptions

什麼情況不能照一般規則？資料衝突時怎麼辦？

4

Definition of Done

什麼品質才真的可以交出去？

Thin skill
Review carefully.
Identify important trends.
Be professional.
Double-check your work.
Knowledge-rich
Prioritize by business impact, not percentage change alone.
Separate facts from hypotheses.
Escalate conflicting sources.
Do not deliver until material numbers reconcile.
四個訪談問題

What do you repeatedly tell Claude? · What do you know that Claude doesn't? · What mistakes would a junior make? · What does “good enough to send” mean?

Case B · Judgment-heavy

報告品質作戰手冊

REAL PROJECT

在高度依賴 AI 產出報告的真實專案裡，最麻煩的不是程式報錯，而是品質會悄悄變差：流程可能被繞過、外部事實可能沒真的查證，但結果仍然看起來像一份正常報告。

這個 Skill 不是「幫我 review 報告」。

它更像一份可重複調用的 quality playbook：保存這個專案到目前為止如何判斷品質、先修什麼、什麼不能為了分數犧牲，以及什麼時候應該停止繼續優化。

1

Sequence Judgment

先修地基，再談優化。
如果前置品質流程沒有真的執行，後面的評分與比較都可能失真。

2

Trade-off Judgment

Accuracy > Score。
即使正確修正讓分數下降，也保留修正；好看的 KPI 不等於真正的品質。

3

Stop Judgment

知道什麼時候夠好。
當核心問題已收斂、剩下主要是風格偏好時，不讓 review 無限循環。

Lesson B

Don't only teach what to do. Teach how you decide what's good enough.

真正值錢的 Skill 往往保存的是那些「新人不一定知道，但有經驗的人腦中會自動跑一次」的判斷標準。

03 · Hands-on · 25 min

現在換你把一件真實工作變成 Skill。

不要選看起來很酷的題目。選你真的做過、之後還會再做，而且你知道好壞差異的工作。

1

Pick

選一個會重複出現、已有做法、結果有品質差異的工作。

2

Teach

讓 Skill Creator 訪談你；提供真實例子、判斷、例外與 bad output。

3

Build

讓 Skill Creator 起草；review 它是否真的捕捉到你的工作方法。

Starter prompt
Use the skill-creator skill to help me turn the following recurring work into a reusable Skill.

Do not draft immediately. First interview me about:
- when this task should trigger
- inputs and outputs
- how I make decisions
- exceptions and edge cases
- what bad output looks like
- what “good enough to send” means

My recurring task is: [describe your task]
  • 我選的是自己真的做過的工作。
  • 我至少提供一個實際 input / output 或具體情境。
  • 我提供至少一條不是照 SOP 就能知道的判斷規則。
  • 我說明至少一個例外或容易犯錯的地方。
  • 我定義了什麼叫「可以直接交付」。
04 · Test & improve

第一版 Skill 不需要完美；它需要可被挑錯。

至少測一個 normal case，再測一個需要 judgment、資料缺漏或來源衝突的 difficult case。

N

Normal case

輸入完整、情境典型。確認 Skill 是否被正確使用，以及 workflow 是否順利。

D

Difficult case

資料缺失、來源矛盾、例外、需要 judgment。這裡最容易暴露 Skill 真正的不足。

症狀通常要改哪一層
該用卻沒用Description / triggering
用了但做法不對Workflow / decision rules / references
看似合理但不能交Definition of done / quality checks / examples
最重要的 review 問題

Would I actually send this output at work? 如果不能，請把「為什麼不能交」直接回饋給 Skill Creator。

Skill 解決 HOW；Automation 解決 WHEN。

Skill 讓工作可重複。排程或 trigger，才讓工作在你沒有手動提醒 Claude 時發生。

Case C · Automated

每日盤前情報工作流

REAL AUTOMATION

這套真實系統曾經每天在盤前自動掃描台美股熱門標的、彙整多個來源、做題材強度判斷、品質檢查，最後把結果送出。

H

High frequency

每天都要做，重複成本會快速累積。

T

Time-sensitive

必須在特定時間窗口完成，晚了價值就下降。

S

Stable workflow

每天內容不同，但處理流程與品質要求相對固定。

A real failure story

「我在旁邊操作時可以」≠「沒有人在旁邊時也可以」

第一次無人值守執行

系統很快結束，沒有 error，也沒有產出——表面上像什麼都沒發生。

不要猜，直接 probe

把幾種呼叫方式在 interactive 與 headless 模式下逐一實測。

找到根因

某個 interactive 能工作的捷徑，在 unattended mode 被安靜地解析成空任務。

修復 + 防復發

換成明確、跨環境都可靠的呼叫方式，並加 regression test 避免未來改回去。

↓

Graceful degradation

某個資料源或判斷模組失敗時，可以走明確退階路徑，但必須誠實標示完整度。

↻

Built ≠ Maintained

這套系統曾在 production 真實運行；目前排程暫停。Automation 仍然需要健康檢查與維護。

Lesson C

Automation changes who presses Start, not whether judgment matters.

自動化不是把 judgment 拿掉，而是把「誰來觸發」拿掉；方法與判斷反而更需要被寫得清楚、可測、可降級。

Wrap-up

選你的下一個 Skill。

  • 這件事之後還會再發生嗎？
  • 我是否每次都在重複解釋類似 instructions？
  • 這件事有「新人不知道、我知道」的 judgment 嗎？
  • 好結果與壞結果之間，有可說清楚的差異嗎？
Skill 存的是你的方法。
判斷力密度決定它值不值錢。
自動化決定它需不需要你在場。
