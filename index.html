01 · Skill 基礎

如果你一直重講同一件事，就把它存成 Skill。

Skill 是一套可重複使用的工作方法。當你每次都貼上相同指示、檢查清單、格式要求或步驟，就值得考慮做成 Skill。

每次重講

規則容易漏，品質容易飄

你必須記得每次要提醒 Claude 什麼。少講一條，結果就可能不同。

存成 Skill

把工作方法固定下來

Claude 遇到相關任務時，可以載入同一套步驟、判斷規則和交付標準。

Skill 結構

Skill 是一個資料夾。入口是 SKILL.md。

my-skill/
├── SKILL.md          # 必要：metadata + 工作指示
├── scripts/          # 選用：可執行程式
├── references/       # 選用：參考資料
└── assets/           # 選用：模板或其他素材
A

Metadata（名稱與用途描述）

name 和 description 放在 YAML frontmatter。用途描述要說清楚 Skill 做什麼、什麼時候該用；這是自動觸發的重要依據。

B

SKILL.md 內文（工作指示）

Skill 啟用後，Claude 才載入完整工作方法。其他參考資料則在需要時再讀。

P

專案 Skill

放在 .claude/skills/<skill-name>/SKILL.md。適合跟著 repository 分享給團隊。

U

個人 Skill

放在 ~/.claude/skills/<skill-name>/SKILL.md。可在自己的不同專案中使用。

不用從空白檔案開始。

Anthropic 官方的 Skill Creator（Skill 建立助手）可以協助你釐清需求、起草、測試和修改。你最重要的工作，是把自己的工作方法講清楚。

案例 A · 簡單

會議筆記 → 可直接寄出的會後摘要

現場示範

這個案例不追求複雜分析。它只解決一件常見的事：每次會議後，都要用同一套格式整理，而且不能亂猜。

Before

每次都要提醒 Claude：整理決議、待辦、未解問題和下次追蹤時間；不要自己補負責人或期限，也不要把「有人提出的想法」寫成「已決定」。

After

Skill 固定輸出四個區塊：已確認決議、待辦事項、未解問題、下次追蹤。筆記沒寫負責人或期限，就直接標示「未指定」。

示範輸入
產品更新會議
- 決定 9/1 先推出 beta
- Amy 說可以研究邀請制，但還沒決定
- Jason 要整理 onboarding FAQ，下週三前給初稿
- 行銷素材誰負責還沒定
- 下次會議 8/30 下午 2 點
示範輸出
已確認決議
- 9/1 先推出 beta。

待辦事項
- 整理 onboarding FAQ 初稿
  負責人：Jason
  期限：下週三

未解問題
- 是否採用邀請制：尚未決定。
- 行銷素材負責人：未指定。

下次追蹤
- 8/30 下午 2 點
注意差異：Skill 沒有替你猜答案。

它做的是固定整理規則：只寫筆記裡有的資訊；沒有負責人、期限或決議，就明確說「未指定」或「尚未決定」。

Lesson A

Skill 不需要很複雜，才值得做。

只要你每次都在重講同一套格式、檢查清單或邊界規則，就可以先把它存起來。

02 · 專業判斷

真正有價值的，是 Claude 原本不知道的判斷。

好的 Skill 不只告訴 Claude「做什麼」，還要告訴它「怎麼判斷做到什麼程度才可以交付」。

1

步驟

事情照什麼順序做？哪些步驟不能跳？

2

判斷

什麼重要？什麼異常？什麼情況值得繼續追？

3

例外

什麼情況不能照一般規則？資料互相衝突時怎麼辦？

4

完成標準

做到什麼程度，才真的可以交給主管、客戶或下一個流程？

太空泛
仔細檢查資料。
找出重要趨勢。
保持專業與正確。
交付前再次確認。
有判斷規則
先看商業影響，不要只看變動百分比。
把已確認事實和推測分開。
來源互相衝突時，不要自行選一個；標示衝突並升級處理。
重要數字沒有和來源核對前，不要交付。
請用四個問題挖出你的經驗。

你最常重複提醒 Claude 什麼？你知道、但 Claude 不知道什麼？新人最容易錯在哪裡？做到什麼程度你才願意直接送出？

案例 B · 判斷密集

把報告品質標準做成一份作戰手冊

真實專案

AI 報告最危險的問題，不一定會報錯。有時流程被跳過、事實沒有查證，報告看起來仍然很正常，但品質已經下降。

所以這個 Skill 不只是「幫我檢查報告」。

它保存的是整套品質判斷：先修什麼、什麼不能為了分數犧牲，以及什麼時候已經夠好，可以停止修改。

1

先修地基

如果前面的品質檢查根本沒執行，後面的評分再漂亮也沒有意義。

2

正確比高分重要

如果修正事實會讓分數下降，仍然要修。好看的分數不等於真正的品質。

3

知道何時停止

核心問題已經解決，只剩風格偏好時，就不要讓檢查無限循環。

Lesson B

不要只教 Claude 做什麼，也要教它怎麼判斷「夠好了」。

最值得保存的，常常是有經驗的人腦中會自動做、但新人不一定知道的判斷。

03 · 動手做 · 25 分鐘

現在，把一件你真的做過的工作變成 Skill。

不要挑「看起來很酷」的題目。挑一件之後還會再做，而且你分得出好結果和壞結果的工作。

1

選

選一件會重複出現，而且已有固定做法的工作。

2

教

讓 Skill Creator 訪談你。提供真實例子、判斷規則、例外和常見錯誤。

3

建

讓 Skill Creator 起草，再確認它有沒有真的抓到你的工作方法。

起手 Prompt
Use the skill-creator skill to help me turn the following recurring work into a reusable Skill.

Do not draft immediately. First interview me about:
- when this task should trigger
- inputs and outputs
- how I make decisions
- exceptions and edge cases
- what bad output looks like
- what “good enough to send” means

My recurring task is: [describe your task]
  • 選的是自己真的做過的工作。
  • 至少提供一個真實輸入、輸出或具體情境。
  • 至少說出一條「新人不一定知道」的判斷規則。
  • 至少說明一個例外或常見錯誤。
  • 說清楚什麼叫「可以直接交付」。
04 · 測試與改進

第一版不用完美，但一定要拿真實情境試。

這堂課至少試兩種情境：一個正常案例，再加一個有缺漏、衝突或例外的困難案例。正式建立 Skill 時，Skill Creator 會依任務類型和你一起決定要不要建立完整的測試案例與評估。

N

正常情境

資料完整、情況典型。先確認 Skill 會被正確使用，而且基本流程能走完。

D

困難情境

加入資料缺失、來源矛盾或例外。這最容易測出 Skill 缺少哪些判斷。

看到的問題優先檢查
該用卻沒用用途描述和觸發條件
用了但做法不對工作步驟、判斷規則和參考資料
看起來合理，但不能直接交完成標準、品質檢查和範例
最後只問一件事：我真的敢把這個結果送出去嗎？

如果不敢，不要只說「再好一點」。把不能交付的具體原因告訴 Skill Creator，讓它修改正確的地方。

05 · 自動化

Skill 決定怎麼做；自動化決定什麼時候做。

先把工作方法做穩，再考慮排程或事件觸發。否則只是把不穩定的流程跑得更勤。

WHEN觸發
WHOClaude Code
HOWSkill
RESULT交付結果
方式適合情境與限制
Routines（研究預覽）在 Anthropic 管理的雲端執行，可用排程、API 或 GitHub 事件觸發；電腦關機也能繼續。
Desktop scheduled tasks需要讀本機檔案或工具時使用。Claude Desktop 必須開著，而且電腦要醒著；錯過的排程可能在之後補跑一次。
/loop適合目前 Claude Code 工作階段中的短期輪詢。必須維持 session；重複任務建立 7 天後會到期。
GitHub Actions適合把 Claude 放進 CI，以 GitHub 的 schedule 或其他工作流程事件執行。
選排程方式前，先問：這個工作需要本機環境嗎？

需要本機檔案或工具，就看 Desktop；需要電腦關機後仍可靠執行，就看 Routines 或 CI；只是在目前 session 短期追蹤，就用 /loop。

案例 C · 自動化

每日盤前情報工作流

真實自動化

這套系統曾在每天盤前自動整理台美股熱門標的：抓資料、判斷題材強度、做品質檢查，再送出結果。

它值得自動化，因為同時符合三個條件：

H

高頻率

每天都要做，重複成本會快速累積。

T

有時效

必須在特定時間完成。晚了，結果的價值就下降。

S

流程穩定

每天資料不同，但處理步驟和品質標準大致固定。

一次真實失敗

「我在旁邊操作時能跑」不代表「沒人在旁邊時也能跑」。

第一次無人值守執行

程式很快就結束。沒有錯誤，也沒有產出，看起來像什麼都沒發生。

不要猜，直接測

把不同啟動方式逐一放進互動模式和無人值守模式測試。

找到原因

其中一種在互動模式可用的捷徑，到了無人值守模式卻被當成空任務。

修好，也防止它再發生

改用兩種模式都可靠的明確啟動方式，再加回歸測試，避免未來又改回有問題的寫法。

↓

失敗時要能降級

某個資料來源失效，不一定要讓整份結果消失。可以繼續產出，但要清楚標示哪些資料不完整。

↻

建好不等於不用維護

這套系統曾經正式自動運行，目前排程已暫停。任何自動化都還是需要健康檢查和維護。

Lesson C

自動化拿掉的是「誰來按開始」，不是專業判斷。

沒有人在旁邊時，工作方法反而更需要寫清楚、測清楚，還要先想好失敗時怎麼處理。

收尾

下一個 Skill，從你明天還會做的工作開始。

  • 這件事之後還會再發生嗎？
  • 我是不是每次都在重複提醒 Claude 同樣的事？
  • 這件事有沒有「我知道，但新人未必知道」的判斷？
  • 我能不能說清楚什麼結果才算可以交付？
