01 · Skill 基礎

Skill 是一份 Claude 可以反覆調用的「工作操作手冊」

當一件工作反覆出現，而你每次都在重新提醒 Claude 相同的範圍、順序、判斷或輸出標準，就有機會把這些內容存成 Skill。

Before

規格活在你腦中

每次重新下 prompt。今天少講一條、明天忘記一個例外，輸出就會飄。

After

規格變成可重複資產

Claude 在相關任務中載入同一套工作方法，人的注意力可以留給新問題，而不是重複交代舊規則。

What lives inside a Skill?

不一定只有一個 prompt

my-skill/
├── SKILL.md          # 必要：用途 + 工作方法
├── references/       # 選用：規範、基準、專案記憶
├── scripts/          # 選用：需要確定性執行的工具
└── assets/           # 選用：模板、素材

簡單 Skill 可能真的只有一份 SKILL.md；複雜 Skill 則可能把規則、參考資料、腳本拆開。不要為了「像一個系統」而硬加零件。

R

重複

同類工作會再次發生。

M

方法

你已經有一套固定做法或輸出規格。

J

判斷

你知道什麼叫好、什麼叫不能交。

案例 A · 簡單 · 教學示例

會議筆記 → 可直接寄出的會後摘要

虛構教學案例

這個案例刻意很簡單：輸入是一段凌亂會議筆記，輸出要變成可以直接寄給團隊的會後摘要。真正要教的不是「摘要能力」，而是怎麼把一句模糊的「幫我整理一下」拆成可重複、可驗收的規格。

Before · 每次重講

「幫我整理會議紀錄。要有決議、待辦、未解問題、下次會議；不要自己猜負責人或期限；提案不能當成已決定。」

After · 存成 Skill

之後只要丟會議逐字稿給 Agent，Agent 便會依照 Skill 去做分類、套格式、處理缺漏，並用預設規則自我檢查。

Mini-spec · 這個 Skill 到底規定什麼？

把「幫我整理」這種模糊任務敘述改寫成 5 條可以判定 Pass / Fail 的具體規則

1

輸出固定四類

永遠依序輸出以下四類：已確認決議、待辦事項、未解問題、下次追蹤。沒有內容也保留區塊並標示「無」。

2

提案 ≠ 決議

只有筆記明確表示「決定、確認、同意採用」的內容才能進決議；「可以研究、建議、考慮」一律不能升格。

3

待辦事項需有三個欄位

每個待辦事項固定具備的輸出項目：事項、負責人、期限。若原文未明確表示負責人或期限，就填「未指定」，不能自行填補人名或日期。

4

分類必須互斥

同一件事項不能同時被歸類為「決議」和「未解問題」。各分類必須互斥，避免摘要看起來自己打架。

5

缺漏要被看見

不知道的資訊要顯式標示，而不是省略。會議摘要的品質標準之一，就是讓人看得出「還缺什麼」。

Acceptance test · 驗收

不要問「你覺得輸出好不好」、不要說「幫我檢查一下」，而是透過 Skill 的指引，讓 Agent 直接自我驗證 5 個指標

透過具體的指標來評估輸出品質，而不是主觀判斷。

驗證標準 檢查內容 合規目標 驗證規則
格式完整率 4 個固定類別區塊是否全部存在？ 4 / 4 規則一：輸出固定四類。
分類誤判 「研究邀請制」是否被錯放成已確認決議？ 0 次 規則二：提案 ≠ 決議。
分類衝突 同一資訊是否重複出現在互相矛盾的分類區塊？ 0 次 規則四：分類必須互斥。
資訊幻覺 缺漏有無明示？是否自行補了不存在的負責人、期限或日期？ 0 次 規則五：缺漏要被看見。
待辦事項之欄位完整率 每個待辦事項是否都有事項／負責人／期限三欄？ 100% 規則三：待辦事項需有三個欄位。
再加一個 edge case

把「下次會議時間」從輸入刪掉，再跑一次。好的 Skill 應該輸出「下次追蹤：未指定」，而不是自己猜一個日期，也不是把整個區塊消失。這就是後面「測試與改進」章節的最小版本。

Lesson A

第一個 Skill 的價值，不是變聰明；是把「好結果長什麼樣」講到可以驗收

固定格式只是開始。真正讓它可重複使用的是：分類規則、禁止事項、缺漏處理與明確的 Pass / Fail 指標。

02 · 專業判斷

真正難複製的，是你「怎麼判斷」

Case A 的規則很容易寫清楚，但真實工作通常更難。Claude 可能照流程走完，卻還是做出你不會交付的結果。下一層要保存的是：順序、取捨、例外、停止條件，以及失敗時怎麼表態。

1

順序

哪些問題沒先處理，後面的數字根本不值得看？

2

取捨

分數、速度、完整度與準確性衝突時，你把什麼排第一？

3

不確定性

查不到、來源衝突、證據不完整時，是猜一個答案，還是明確標示限制？

4

停止

做到什麼程度，就應該停止繼續優化？

課堂小練習

想一件你會交給新人做的工作：你驗收時腦中會快速掃過哪 3 條判準，但從來沒真正寫下來？那通常就是 Skill 最值錢的素材。

案例 B · 判斷密集

讓下一份 AI 報告少犯同樣的錯

真實專案

這個專案用 AI 產出深度研究報告。最大的風險不是格式不好，而是報告看起來完整，日期、數字或推論卻可能錯。為了避免同一類問題一再發生，我把「怎麼查、怎麼修、什麼時候可以停止」寫進品質 Skill。每次發現新錯誤，都再判斷：這只是單次問題，還是下一份報告也該固定檢查？

只修這份報告

這次改對，下次可能再錯

把錯誤數字改掉，可以救這份報告。但經驗沒有留下，下次遇到同類問題，Claude 仍可能再犯。

留下檢查規則

這次抓到的錯，變成下次固定檢查

如果時間線、單位或來源問題反覆出現，就把它寫進 Skill。下一份報告會直接多一道檢查，不用再從零學一次。

真實案例

第一輪審查就抓到 12+ 個問題

其中有兩類重大事實錯誤：產品時程寫錯，以及市場規模數字引用錯誤。

只改這兩個答案，只能救這一份報告。品質 Skill 還要找出錯誤類型，決定下次應在哪一步檢查。

重點：修報告解決今天；改規則才會改善下一次。
一份報告要能交付

先走完 4 個檢查，再決定能不能交

1. 先確認檢查真的有執行

曾經有一份正式報告完全繞過品質流程。這時任何分數都不可信。先確認查證與審查都有完成，再看結果。

2. 重要數字和時間線重新查

不要沿用原本的搜尋答案。換一組查法，至少用兩個獨立來源交叉確認，並重算衍生數字。只要查證失敗或重算不一致，就先修正，不交付。

3. 讓另一個審查角色只看完成稿

審查者不看撰寫過程，避免替原答案找理由。它把問題分成事實錯誤、方法缺口、風格建議；有證據且影響品質的問題才修。

4. 問題只剩風格時，才考慮停止

如果第三輪還在抓重大事實錯誤，代表不能停。當一輪只剩風格建議，而且沒有實質修正值得採用，才表示結果已接近可交付。

真實四輪審查紀錄

用問題類型判斷是否收斂，不是死守四輪

輪次發現問題採用修正看到的變化
第 1 輪12+ 個約 6 個仍有重大事實錯誤，例如時間線和關鍵數字。
第 2 輪6 個4 個重大錯誤下降，開始剩研究方法與解釋方式的缺口。
第 3 輪4 個4 個繼續補方法與說明，仍有值得修正的內容。
第 4 輪3 個0 個只剩風格建議，沒有實質修正被採用，可以停止。

這個紀錄不是規定每份報告都要審四輪。它讓團隊知道正常的改善應該長什麼樣：重大事實錯誤先下降，再剩方法問題，最後才是風格。如果重大錯誤到第三輪還在出現，就要回頭檢查前面的產出流程。

Skill 裡還保存哪些判斷？

五條規則，讓團隊不必每次重新猜

這些規則都直接影響報告能不能交付。

01準確比高分重要修正後分數降低，也要保留正確答案＋

如果修正讓報告更符合事實，就保留修正。不能為了維持漂亮分數，把已知錯誤留在報告裡。

02無法驗證，就明確標示不知道的地方不要寫成已證實＋

只有單一來源、無法獨立確認的說法，要清楚標示限制。讀者需要知道哪些資訊已確認，哪些仍有不確定性。

03改一個數字，要連帶重算前後不能同時留新舊答案＋

基礎數字改了，相關比率、結論和後文引用都要一起重算、檢查。否則前面雖然改對，後面仍可能留著舊答案。

04同類錯誤再出現，就新增檢查不要只要求下次更小心＋

如果不同報告反覆出現時間線計算或單位混淆，就代表流程少了一道檢查。把新檢查寫回 Skill，讓下一次自動套用。

05先證明有需要，再增加規則避免 Skill 越寫越長卻沒有幫助＋

想到一個可能有用的改善，不代表現在就要加入。先用真實報告證明問題確實存在，再增加檢查，避免規則無限膨脹。

這份 Skill 真正保存什麼？

不是投資知識，是團隊的驗收方法

A

先做什麼

先確認流程有跑，再查事實；先修重大錯誤，再談方法與風格；不能因為分數高就放過錯誤。

B

怎麼從錯誤學習

這次錯在哪 → 哪些要修 → 是否重複發生 → 要不要加成固定檢查。下一份報告不用再從零開始。

Lesson B

把高手的驗收判斷寫下來，團隊就不必每次靠感覺

Skill 要保存的是：哪裡最容易錯、什麼證據才夠、什麼情況不能交、什麼時候可以停止。這些判斷越清楚，品質越能穩定重複。

03 · 動手做 · 約 23 分鐘

把一件你真的做過的工作交給 Skill Creator 訪談

不要從「我想做一個很厲害的 Skill」開始。先選一件明天、下週、下個月還會再做的工作，而且你知道什麼叫做得好。

1

選工作

會重複、已有固定做法，而且有明確好壞差異。

2

講案例

提供真實輸入／輸出、例外、踩坑與不能接受的結果。

3

讓它追問

不要急著叫它直接生成；先讓 Skill Creator 把你腦中的隱性判斷問出來。

起手 Prompt
Use the skill-creator skill to help me turn this recurring work into a reusable Skill.

- when this task should trigger
- inputs and expected outputs
- the steps I normally follow

- exceptions and failure cases
- what bad output looks like

My recurring task is: [describe your real task]
  • 至少給一個真實情境，不要只講抽象需求。
  • 至少說出一條「新人不一定知道」的判斷。
  • 至少說出一個例外或常見失敗。
  • 說清楚哪種結果即使看起來完整，你也不會交。

04 · 測試與改進

拿真實情境試，不要只讀 SKILL.md 覺得「看起來合理」

第一版最容易出現的問題，不一定是語法錯，而是它根本沒抓到你真正的判斷。至少跑一個正常案例，再跑一個有缺漏、衝突或例外的困難案例。

你看到的症狀優先回頭看
該用 Skill 卻沒用名稱／用途描述／何時應觸發
用了，但步驟不對流程、參考資料、工具邊界
流程都跑了，判斷還是不像你判斷規則、取捨、例外、反例
結果看起來完整，卻不能直接交完成標準、品質檢查、失敗表態方式
一個實用的改進循環

不要問「怎麼讓 prompt 更厲害？」；問「這次輸出和我真正想要的結果差在哪？這個差異背後缺的是規格、判斷、資料，還是完成標準？」

F

每天資料不同，但處理框架穩定。

案例 C · 自動化 · 真實系統

每天 08:20，自動把盤前重點送到團隊

已完成端到端驗證

這個案例不是要教投資，而是看一件每天都要準時完成的工作，怎麼從「人每天早上記得做」變成「系統自己開始、自己判斷能不能交付、失敗自己重試」。真實流程會先掃描台股與美股，各選出 10 檔，再查最多 20 檔的新聞催化，最後只發一則短訊到 Discord。

Why automate this?

早上 08:20 要開始；但不值得每天安排一個人只負責「按開始」

盤前資訊每天不同，但工作順序固定，而且晚了價值就下降。這正是適合自動化的工作：把「何時開始」交給排程，把「怎麼做、什麼算完成」留在 Skill。

把技術細節拿掉後，核心其實只有 5 個動作

每一步都有明確的完成條件，不是「有跑就算成功」。

台股看成交活躍度、價格動能與籌碼；美股看成交量與漲跌幅。先縮小範圍，再把時間花在真正值得看的標的。

03NEWS

替最多 20 檔補上新聞催化

Claude 再搜尋近期新聞，補充「今天為什麼值得注意」。外部內容只當資料，不把網路上的文字當成系統指令。

04MESSAGE

濃縮成一則短訊

訊息上限 1,900 字。內容太長時先縮到每個市場前 8 檔，再刪減註記；不是拆成一串訊息轟炸團隊。

05DELIVER

真的送達，才記「今天完成」

只有 Discord 接收成功後，系統才留下今日成功標記。送失敗就不能假裝完成，因為這個標記會決定今天還要不要重跑。

教材不展示 webhook、API 金鑰、實際股票名單與真實推播內容；這些不是理解自動化設計所必需的資訊。
例外不是「全部失敗」

真正可用的自動化，要先寫清楚：什麼情況照樣交、什麼情況一定要重試

早上發生的事系統怎麼做團隊會看到什麼
台股資料暫時抓不到美股照常繼續，不讓一邊的問題拖垮整份結果。仍可收到可用內容，但會標示哪一邊資料不完整。
週末或市場休假，沒有新資料不硬湊一則「今日熱股」，只記錄今天已正常檢查完成。沒有訊息反而是健康狀態，不代表系統壞了。
訊息第一次送不出去不寫成功標記；15 分鐘後再試，仍失敗則 60 分鐘後再試。短暫的外部服務異常不需要人立刻介入。
連續 3 次都失敗停止無限重試，改送一次失敗通知，讓人知道要接手。自動化有明確的「交回給人」時機。
為什麼需要三份 Skill 文件？

一份講「正常怎麼跑」，另外兩份把失敗經驗與日常維護留下來

自動化不是只需要一份流程文件。系統活得越久，越需要把「為什麼這樣設計、以前怎麼壞、今天沒收到要先查什麼」分開保存。

WHYArchitecture Contract正常流程與「不能被改壞」的規則＋

例如：只有真正送達才算成功；台股或美股單邊失敗時，另一邊仍可交付；秘密金鑰不能出現在程式碼或日誌。這份文件保存的是系統的設計底線。

PASTFailure Archaeology以前真的踩過哪些坑＋

它記錄真實事故與修法，例如：互動模式可用的捷徑，在無人值守模式其實看不到。下次遇到相似症狀，先比對舊事故，不要急著重做整套系統。

OPSOps Runbook今天沒收到訊息，先查哪裡＋

固定從「今天有沒有成功標記」開始，再看排程程序是否存活、日誌寫了什麼、重試到第幾次。讓維運像 checklist，而不是每次靠資深同仁臨場猜。

Failure story · 真實事故

第一個無人值守版本，12 秒就結束：沒有錯誤訊息，也沒有任何產出

1. 表面看起來「有啟動」

排程確實叫起了 Claude，但 12 秒後就結束，沒有推播，也沒有今日成功標記。

2. 成功標記讓問題無法被假裝成成功

因為「有執行」和「有送達」是兩件事。沒有成功標記，就代表今天這次工作還沒完成。

3. 根因不是資料，也不是選股邏輯

真正原因是：互動畫面裡可以使用的 plugin 捷徑，在無人值守模式（沒有人在畫面前操作）不會載入。Claude 實際收到的是一個空任務，所以很快就結束。

4. 修法是把任務說得更直接

排程不再依賴互動捷徑，而是明確指定要讀哪一份 Skill、照哪幾步執行；並加上自動測試，避免未來又改回會失效的寫法。

脆弱的自動化

排程有啟動，就以為工作完成

遇到假日、部分資料失敗、外部服務短暫故障時，很難分辨「正常安靜」和「真的壞掉」。

可維運的自動化

每種狀態都有下一步

正常就送達並留標記；沒新資料就安靜完成；部分資料壞掉就降級；送不出去就重試；連續失敗就交回給人。

Lesson C

自動化不是把人拿掉；是先把「什麼算完成、失敗怎麼辦」講清楚

當 Skill 已經寫清楚正常流程、降級方式、重試規則與成功標準，排程才有資格拿掉「每天誰來按開始」這件事。這也是業務流程自動化最值得複製的設計思路。

收尾

Skill 存的是你的方法；判斷力密度決定它值不值錢；自動化決定它需不需要你在場

  • 這件事之後還會再發生嗎？
  • 我是不是一直在重講同樣的規格？
  • 裡面有沒有「我知道，但新人未必知道」的判斷？
  • 我能不能說清楚什麼情況不能交付？
  • 如果它同時高頻率、時間敏感、流程固定，是否值得把觸發也自動化？
不要從「我要做一個 Skill」開始。
從「我有哪個工作方法值得保存」開始。

Work → Skill → Judgment → Automation
