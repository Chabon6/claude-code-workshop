01 · Skill 基礎

Skill 是一份 Claude 可以反覆調用的「工作操作手冊」

當一件工作反覆出現，而你每次都在重新提醒 Claude 相同的範圍、順序、判斷或輸出標準，就有機會把這些內容存成 Skill。

Before

規格活在你腦中

每次重新下 prompt；今天少講一條、明天忘記一個例外，輸出就會飄。

After

規格變成可重複資產

Claude 在相關任務中載入同一套工作方法，人的注意力可以留給新問題，而不是重複交代舊規則。

What lives inside a Skill?

不一定只有一個 prompt

my-skill/
├── SKILL.md          # 必要：用途 + 工作方法
├── references/       # 選用：規範、基準、專案記憶
├── scripts/          # 選用：需要確定性執行的工具
└── assets/           # 選用：模板、素材

簡單 Skill 可能真的只有一份 SKILL.md；複雜 Skill 則可能把規則、參考資料、腳本拆開。不要為了「像一個系統」而硬加零件。

R

重複

同類工作會再次發生。

M

方法

你已經有一套固定做法或輸出規格。

J

判斷

你知道什麼叫好、什麼叫不能交。

案例 A · 簡單 · 暫定 fallback

副業／側收入探索進度儀表板

真實既有 Skill
案例狀態要講清楚

這是目前 handoff 保留的真實 fallback，尚未被最終確認為正式 Case A。網站不再用虛構的「會議摘要」取代它。

它只做一件很簡單的事：當我想知道「副業探索現在到哪裡」，不用每次重新交代要看哪些資料、用什麼格式呈現；講一個觸發詞，就把既有狀態按固定結構整理出來。

Before · 推測還原

「幫我看一下副業探索進度：我的背景、候選機會、正在做的項目、過去復盤，最後告訴我下一步。」每次都要重新講範圍，而且容易漏掉其中一塊。

After · 真實設計

Skill 只讀既有狀態檔，固定輸出五個區塊，再依當下狀態建議下一個應該使用的兄弟 Skill。

Inside the real Skill

這個 Skill 真正保存的是「固定查看規格」

1

讀狀態，不改狀態

它是純唯讀工具：安全地查看目前進度，不會因為呼叫它而改掉任何資料。

2

固定五個資訊區塊

背景畫像、候選機會、執行中項目、過去復盤等資訊都按固定結構呈現；教材只展示欄位概念，不展示真實敏感值。

3

固定下一步邏輯

例如目前沒有候選、還有未查證候選、已有可行機會但尚未選定，會導向不同的後續動作。

4

沒有腳本也沒關係

原 Skill 結構很薄，重點就是把「每次都要重講的查看規格」固定住。

Lesson A

值得存下來的，不一定要很聰明

只要一套格式或查看範圍反覆出現，固定它就能換來一致性和省力。這是 Skill 價值光譜最簡單的一端。

02 · 專業判斷

真正難複製的，是你「怎麼判斷」

如果只把步驟寫下來，Claude 可能照流程走完，卻還是做出你不會交付的結果。下一層要保存的是：順序、取捨、例外、停止條件，以及失敗時怎麼表態。

1

順序

哪些問題沒先處理，後面的數字根本不值得看？

2

取捨

分數、速度、完整度與準確性衝突時，你把什麼排第一？

3

不確定性

查不到、來源衝突、證據不完整時，是猜一個答案，還是明確標示限制？

4

停止

做到什麼程度，就應該停止繼續優化？

課堂小練習

想一件你會交給新人做的工作：你驗收時腦中會快速掃過哪 3 條判準，但從來沒真正寫下來？那通常就是 Skill 最值錢的素材。

案例 B · 判斷密集

報告品質系統性提升作戰手冊

真實專案

這個專案幾乎純靠 AI 產出報告。最危險的不是程式報錯，而是品質悄悄變差：規則沒有真的被遵循、外部事實沒有真的查證，報告看起來仍然完整，但其實已經偏掉。這類事故曾經真的發生過：一份正式交付報告完全沒有跑到品質檢查。

The real problem

一次修一個錯，不代表品質系統在變好

這份 Skill 的作用不是替某一份報告挑錯，而是把「目前有哪些品質防線、真實量測基準在哪、每一輪品質提升要怎麼跑、什麼時候算收斂」收斂成一份可重複使用的專案品質記憶。

Inside the real Skill

打開這份作戰手冊，實際會看到什麼？

以下都來自 handoff 可確認的真實結構；敏感的個股、投資內容與實際數值不展示。

01先過前置閘門品質流程沒有真的跑到，後面分數都不可信＋

先檢查品質流程是否真的被執行，以及需要查證的外部事實是否真的查過。這不是「提醒一下」，而是先決條件。

判斷：先把地基修好，再談優化；否則你只是在精確量測一個錯誤流程。
02盤點已經存在的品質槓桿先知道專案現在到底有哪些防線＋

手冊會整理分散在不同文件裡的品質機制，例如初始協調規則、事實查證規則、評分規則。下一次改善時，不用重新靠記憶拼湊。

03保存真實量測基準看得出品質是不是逐輪收斂＋
  • 第一輪：最多、最嚴重的錯誤。
  • 中間幾輪：開始剩方法論類問題。
  • 最後：只剩風格類意見，分數也不再變動。

這組真實審查紀錄提供一個「什麼叫正在收斂」的參考形狀，而不是只靠感覺。

04定義每輪品質提升怎麼打不是看到哪裡錯就隨手修哪裡＋

Skill 保存每跑一輪「品質提升作戰」時要完成的固定工作，使改善變成可重複的回合。handoff 沒有列出這 5 個子步驟的逐條內容，因此教材也不自行補造。

05用計分誘因防止偷懶完成一輪有小獎勵，嚴重錯誤沒修會付更大代價＋

這不是要追求漂亮分數，而是把「跳過修正」變成不划算的選擇。規則本身在塑造代理的行為，而不只是事後評論結果。

06把價值排序寫死準確優先於分數好看＋

手冊明確記錄：如果一個修正讓結果更準確，即使分數因此下降也要保留。這是在保存人的取捨，不只是保存流程。

07候選改善 ≠ 已驗證能力聽起來有用，不代表現在就應該加進系統＋

尚未在實戰證明必要的點子明確標成 Candidate。這是在對抗過度工程，也讓 Skill 誠實區分「已驗證」與「可能有用」。

08連 Skill 本身也要重新驗證專案變了，作戰手冊也可能過時＋

文件結尾保留如何重新驗證這份手冊是否過時的具體指令。Skill 不是寫完就永遠正確，它本身也需要維護。

What is actually being stored?

這不是「一個很長的 prompt」，而是一套品質決策系統

A

專案記憶

已經做過哪些改善、有哪些品質機制、真實基準線在哪。

B

價值判斷

先修什麼、怎麼取捨、查不到怎麼表態、什麼時候停止。

Lesson B

Skill 可以保存「你怎麼把事情做對」的整套方法

判斷力密度越高，Skill 越不像模板，也越像可以反覆調用的專業。

03 · 動手做 · 約 23 分鐘

把一件你真的做過的工作交給 Skill Creator 訪談

不要從「我想做一個很厲害的 Skill」開始。先選一件明天、下週、下個月還會再做的工作，而且你知道什麼叫做得好。

1

選工作

會重複、已有固定做法，而且有明確好壞差異。

2

講案例

提供真實輸入／輸出、例外、踩坑與不能接受的結果。

3

讓它追問

不要急著叫它直接生成；先讓 Skill Creator 把你腦中的隱性判斷問出來。

起手 Prompt
Use the skill-creator skill to help me turn this recurring work into a reusable Skill.

Do not draft immediately. Interview me first about:
- when this task should trigger
- inputs and expected outputs
- the steps I normally follow
- how I make decisions and trade-offs
- exceptions and failure cases
- what bad output looks like
- what “good enough to send” means

My recurring task is: [describe your real task]
  • 至少給一個真實情境，不要只講抽象需求。
  • 至少說出一條「新人不一定知道」的判斷。
  • 至少說出一個例外或常見失敗。
  • 說清楚哪種結果即使看起來完整，你也不會交。
  • 檢查 Skill Creator 是否把你的方法寫對，而不是只檢查格式漂亮。
04 · 測試與改進

拿真實情境試，不要只讀 SKILL.md 覺得「看起來合理」

第一版最容易出現的問題，不一定是語法錯，而是它根本沒抓到你真正的判斷。至少跑一個正常案例，再跑一個有缺漏、衝突或例外的困難案例。

你看到的症狀優先回頭看
該用 Skill 卻沒用名稱／用途描述／何時應觸發
用了，但步驟不對流程、參考資料、工具邊界
流程都跑了，判斷還是不像你判斷規則、取捨、例外、反例
結果看起來完整，卻不能直接交完成標準、品質檢查、失敗表態方式
一個實用的改進循環

不要問「怎麼讓 prompt 更厲害？」；問「這次輸出和我真正想要的結果差在哪？這個差異背後缺的是規格、判斷、資料，還是完成標準？」

05 · 自動化

Skill 決定怎麼做；自動化決定什麼時候開始做

不是所有 Skill 都值得排程。最適合往自動化推進的工作，有三個共同特徵：高頻率、時間敏感、流程固定——內容每天可以不同，但「怎麼做」大致穩定。

H

高頻率

一再重複，人工觸發本身已經是負擔。

T

時間敏感

早一小時或晚一小時，價值可能就不同。

F

流程固定

每天資料不同，但處理框架穩定。

案例 C · 自動化

每日盤前熱股掃描與推播

曾真實生產運行

每天盤前自動掃描台美股熱門標的，整合多個情報來源，再讓一個專職 AI 子代理判斷題材處於「剛升溫／高潮／退燒」，最後自行組成訊息、品質檢查並發送。它的價值不是「會選股票」，而是示範一個 Skill 怎麼進入無人值守工作流。

Why automate this?

內容每天不同，但流程每天一樣，而且必須在盤前完成

高頻率 + 時間敏感 + 流程固定，正是「連觸發本身都值得交出去」的典型組合。

Inside the real Skill · 執行層

原始文件是一份完整 8 步驟協定；教材只展示 handoff 明確支持的 7 個核心環節

這裡刻意不自行猜測或補造未在 handoff 展開的第 8 個步驟。

1 / 7
01SCREEN

量化篩選

先用量化條件縮小候選範圍，讓後面的情報工作集中在值得看的標的。

02FEEDBACK

命中率回填／週報

把過去執行結果回填，保留週期性回顧；系統不是每天重新失憶。

03SOURCES

七個情報來源獨立抓取

來源彼此隔離，一個來源掛掉不會拖垮整條流程。

04VALIDATE

訊號萃取與驗證

不合格資料直接拒收，不為了「看起來完整」而硬塞進結果。

05JUDGE

專職子代理做題材裁決

一個純推理、不使用工具的子代理，把題材分成「剛升溫／高潮／退燒」；失敗時有兩階段退階方案。

06COMPOSE

組訊息 + 發送前品質檢查

輸出有固定格式契約，而且在真正送出前再做一次品質檢查。

07DELIVER

發送並寫入成功標記

只有真正發送成功，才允許留下「成功」狀態。

實際 webhook、API 金鑰、股票代碼、投資判斷與真實訊息內容不在教材展示。
Inside the real Skill · 支援層

另外三份文件，保存「為什麼、壞過什麼、平常怎麼顧」

WHY設計意圖為什麼當初要這樣設計＋

避免未來只看到「現在怎麼做」，卻把當初的重要取捨刪掉。

BUG故障目錄以前怎麼壞、最後怎麼修＋

真實失敗模式與修法被留下來，讓系統不必每隔幾個月重新踩同一個坑。

OPS日常運維做完自動化之後，平常怎麼維護＋

自動化不是「設定一次就永遠存在」，它同樣需要健康檢查與維護。

Failure story

這個案例最值得教的，不是成功，而是第一次無人值守時「安靜地什麼都沒做」

第一次自動跑：秒結束、沒報錯、沒產出

表面上看起來像什麼都沒發生，因此不能用傳統「找錯誤訊息」的方法定位。

不要猜，做一比一探測

同樣幾種呼叫方式，分別在互動模式與無人值守模式實測。

找到根因

某種互動模式可用的捷徑，在無人值守環境被靜默解析成空任務；模型其實收到的是「什麼都沒有」。

修好後，加測試防止復發

改成明確、直接的呼叫方式，再用自動化測試把這個修法釘死。

D

多層降級

某個來源或子代理失敗時，流程不是只能「全成或全敗」；可以降級，但要誠實標示資訊不完整。

N

明確禁止事項

發送失敗不能寫成功標記；外部抓回來的文字也不能被當成系統指令執行。

歷史事實

曾經真實每天自動執行

有生產環境運行紀錄與狀態時間戳，也有 30+ 筆迭代提交記錄。

目前狀態

已建置、已驗證、目前暫停

排程常駐程序目前沒有運行。這不是「沒做完」，而是自動化系統也需要運維的真實狀態。

Lesson C

自動化拿掉的是「誰來按開始」，不是判斷力

訊號驗證、題材裁決、降級、品質門檻都還在；只是不用人每天早上記得叫它開始。

收尾

Skill 存的是你的方法；判斷力密度決定它值不值錢；自動化決定它需不需要你在場

  • 這件事之後還會再發生嗎？
  • 我是不是一直在重講同樣的規格？
  • 裡面有沒有「我知道，但新人未必知道」的判斷？
  • 我能不能說清楚什麼情況不能交付？
  • 如果它同時高頻率、時間敏感、流程固定，是否值得把觸發也自動化？
不要從「我要做一個 Skill」開始。
從「我有哪個工作方法值得保存」開始。
